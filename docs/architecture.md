# DDGo architecture

This document summarizes the current code structure for contributors. It describes what exists now and calls out intentionally deferred behavior.

## Controller

`internal/app.Controller` is the application orchestration layer. It owns:

- connection state and the active transport;
- the application event stream;
- the loaded G-code program;
- the active program run, when one is running;
- the macro engine hook;
- the optional motion rewriter hook;
- the process-local variable store;
- contour state;
- last successful probe point state.

The controller coordinates these concerns but keeps lower-level details in focused packages: transport I/O is in `internal/transport`, GRBL command and status helpers are in `internal/grbl`, G-code loading/parsing is in `internal/gcode`, and macro framework types live in `internal/macro`.

The controller owns status-poll cancellation and waits for the polling goroutine to stop during either explicit or unexpected disconnect cleanup. The serial transport owns its read loop and line buffer; partial serial lines are scoped to one connection and are discarded before a replacement read loop starts.

Connection establishment has an explicit public lifecycle: `disconnected -> connecting -> connected`. The `connecting` phase covers opening the transport, observing a GRBL startup banner, allowing startup output to settle, and validating a `$$` settings response. Numeric settings are collected privately during validation and copied into a connection-generation-owned snapshot only when that candidate generation commits; disconnect clears the snapshot. Successful numeric setting assignments update that snapshot only after their matching terminal `ok`. `$RST=$` and `$RST=*` invalidate it before their transport write because firmware reset may prevent a normal acknowledgement; `$RST=#` does not change global timing settings. The physical transport generation is committed and normal status polling begins only after initialization succeeds.

Response-owning controller command APIs enforce one physical serial line per logical operation by rejecting command text containing CR or LF before response ownership or expected-silence setup. Raw realtime messages such as status, hold, resume, reset, and jog cancel use their separate byte-oriented path and are not subject to this line-command invariant.

## Controller health and emergency stop

A transport disconnect and a connected-but-unresponsive controller are separate states. Loss of the serial transport follows normal disconnect cleanup. While the transport remains open, controller-owned `?` polling runs every 500 ms. Any accepted RX from the committed, actively monitored transport generation proves controller liveness and satisfies an outstanding heartbeat when the line was received at or after that heartbeat began. Once at least one status request has been issued, roughly two seconds without qualifying controller RX enters the explicit e-stop state while keeping the connection and its transport generation committed. A parsed `ALARM:50` enters the same state immediately; other GRBL alarm codes do not.

That timeout is DDGo's current classification, not definitive proof that the controller stopped executing or that a physical e-stop occurred. The GG3 firmware has command- and state-specific periods in which controller output can be intentionally unavailable: homing and leveling can defer status servicing entirely. A critical alarm can instead answer `?` without sending a normal `<...>` report; that answer proves liveness but does not have parsed-status recovery semantics. See [`docs/gg3-firmware-status-silence.md`](gg3-firmware-status-silence.md) for the firmware behavior and resulting design constraint.

The controller also has a private, command-owned expected-silence lease mechanism. GG3 `$H`, `$HX`, `$HY`, `$HZ`, `$L`, and `$LS` commands install a generation- and operation-specific lease before their transport write when the committed connection has a complete usable timing-settings snapshot. Lease timing is calculated from the retained homing, axis-rate, acceleration, and travel settings; missing or invalid settings conservatively leave the ordinary watchdog active. A lease abandons the ordinary heartbeat and suppresses controller-owned background `?` probes without stopping the polling goroutine. Current-generation RX refreshes lease activity but does not complete the operation; a terminal `ok`, `error`, or `ALARM` response, owner teardown, reset, disconnect, or e-stop ends it. `$L` adjustment output also tightens the next finite inactivity interval while retaining the same operation token; its numeric coordinate-report value is normalized back to internal millimeters using the committed `$13` setting before timing and travel clamping. Lease expiry uses the existing unresponsive e-stop transition.

Expected silence accepts an unavoidable observability tradeoff in the examined GG3 firmware. During firmware-blind homing or leveling, a physical e-stop can occur while USB remains connected and the firmware is not servicing realtime serial requests. DDGo cannot distinguish that event from legitimate blind execution until communication resumes or the finite command-specific inactivity limit expires. The conservative motion bound and margin therefore increase worst-case e-stop detection latency relative to ordinary operation. Background `?` requests are not flooded during the blind phase because they add no information and the firmware coalesces them. When output resumes, `ALARM:50` still takes immediate precedence; if it never resumes, lease expiry enters `EStopSourceUnresponsive`.

Entering e-stop cancels the current response session, fails and cancels active or paused program work, disables contour execution, and invalidates cached machine position, work position, offset, feed, spindle, and status telemetry. Ordinary machine commands are rejected by controller admission while e-stop is active. Status probing continues independently so a command goroutine blocked waiting for `ok` cannot prevent timeout detection. A fresh valid status proves that communication recovered: an `Alarm` or other non-Idle status advances to recovery, where reset and unlock are allowed, while a fresh `Idle` status clears the e-stop state. A failed program is never resumed automatically.

The watchdog and all health transitions are tied to the exact committed transport generation, so delayed activity from an older connection cannot affect a replacement connection. A real transport disconnect clears e-stop state and wins any race with watchdog detection. Serial writes remain synchronous at the transport boundary; the watchdog can still update controller state while a write is blocked, although an operating-system write that never returns can delay that writer's cleanup and an explicit disconnect waiting for its I/O reservation.

The behavior is informed by the legacy research in [`docs/ddcut estop detection temp reference.md`](ddcut%20estop%20detection%20temp%20reference.md), without adopting DDCut's synchronous response-loop timeout design or its manual-operation timeout exception.

## Program execution

Current program execution flow:

1. A G-code file is loaded through `internal/gcode`.
2. Each runnable line is preserved as both raw text and sanitized text.
   - Raw text is trimmed input after BOM removal.
   - Sanitized text removes comments and normalizes whitespace.
3. Starting a program creates an active program run and marks the controller state as running.
4. For each parsed program line, the run loop:
   - waits until the run is not paused;
   - dispatches the line to the macro engine if one is configured;
   - if no macro handler handles the line, passes it through the optional motion rewriter;
   - sends the resulting line and waits for a terminal controller response: `ok`, `error`, or `alarm`;
   - updates program progress.
5. The controller marks the program completed after all lines finish, or failed when send, macro, rewrite, query, or controller response handling returns an error.

Program execution has two independent identities. A `DocumentID` identifies the originating application document without relying on its filename or path; zero denotes the legacy globally loaded-program workflow. Every successfully admitted execution receives a new, nonzero controller-owned `RunID`. The controller publishes both identities with program status and progress in its revisioned state snapshots, and retains them through pause, resume, completion, failure, and stop so delayed UI events remain attributable to their original run.

Program failure attribution is explicit. `State.LastError` remains the controller-wide most recent error used by the existing main window, while `State.ProgramError` contains only the failure reason belonging to `State.ProgramRunID`. An `EventError` identifies a run only when its nonzero `ErrorRunID` is populated; `ErrorDocumentID` then identifies its originating document and may be zero for a legacy run. Program identity present in an error event's state snapshot is contextual and does not associate a general error with that run. Unrelated admission, validation, transport, or manual-command errors may replace `LastError` without changing `ProgramError`.

`StartDocumentProgram` admits a document identity and an independently copied `gcode.Program` snapshot as one controller operation. Snapshot selection, response-owner acquisition, run-ID allocation, active-run installation, and public state attribution occur under the same controller admission lock. A competing request therefore cannot replace the active program or its identity. The legacy `LoadProgramFile`/`StartProgram` interface uses the same run admission path; file loading revalidates active execution after file I/O before replacing the legacy loaded program. Programs can also be parsed directly from a `gcode.Document`'s retained source, preserving physical line numbers without rereading a filesystem path.

`PauseProgramRun`, `ResumeProgramRun`, and `StopProgramRun` bind document controls to an exact `DocumentID`/`RunID` under controller admission and again at realtime-write reservation. A zero `DocumentID` remains valid for the legacy loaded-program workflow, but every run-aware action requires a nonzero `RunID`; an old UI callback cannot hold, resume, or abort a replacement execution. The unscoped methods remain for established legacy callers. After the final command acknowledgement, a run remains active in `ProgramDraining` with its response ownership intact until a status report newer than the final-command baseline reports firmware `Idle`. This is evidence that the firmware's outstanding work has drained, not independent physical verification of cutter position. A draining run can be paused; resume returns it to draining without resubmitting instructions. Pause uses one exact, private transition token per run: an overlapping Pause is rejected and cannot clear the accepted operation's completion interlock. The same run and token are revalidated while atomically reserving realtime transport, preventing a delayed Hold from reaching a replacement run. Pending Pause blocks completion, and even a failed Pause invalidates the earlier drain synchronization so a new qualifying Idle is required.

Program termination and machine execution readiness are separate controller facts. A normally completed run has already crossed the fresh-Idle drain boundary. An interrupted or failed run may leave acknowledged motion buffered, so terminal `ProgramFailed` does not by itself permit another run or ordinary machine command. `State.MachineReadiness` provides the independent interlock: its zero/normal value permits ordinary admission, while `Stopping`, `Verifying`, and `RecoveryRequired` block new programs, interactive macros, manual G-code, jogging, spindle/motion commands, and Resume. Status monitoring, emergency safety actions, reset/unlock recovery, and disconnect/reconnect remain available. During `RecoveryRequired` after an ordinary observed firmware Alarm, the explicit `$X` Unlock action is allowed only when no program or Stop coordinator owns execution; it can clear the firmware alarm but never establishes host machine readiness. `MachineReadinessReason` supplies the operator-facing explanation; clearing an e-stop latch or acknowledging Unlock does not clear this independent interlock.

An accepted Stop first publishes `ProgramStopping`, cancels instruction submission and the program response session, and claims one run-, document-, and connection-generation-specific abort operation. Caller context cancellation may stop that caller from waiting, but the bounded controller-owned coordinator continues. It waits behind an already-admitted Pause or status write with foreground priority, then holds one realtime-write reservation across Hold followed by Ctrl-X. Repeated Stop requests do not issue duplicate abort sequences, and the exact run/generation checks prevent a stale stop or pause callback from acting on a replacement execution. A recovery disconnect may retire a Stop reservation that is stuck in an operating-system write only after a successful physical transport close; cancellation or a controller timeout alone does not prove the old write ended. The serial transport captures its port handle before a write, so a delayed old-generation write cannot be redirected to a newly opened port. If close fails, DDGo keeps the recovery interlock and does not report a successful disconnect.

Ctrl-X write completion is not reset confirmation. For the examined GG3 firmware (`Defdist/grbl1v1g_GG3_GrBLDC3v0` revision `b42f8e461506e75b2d0b5d9014e64c323a49608d`), `mc_reset()` raises `EXEC_ALARM_ABORT_CYCLE` (`ALARM:3`) when it interrupts active motion, then returns control to the initialization loop in `grblDD/main.c`, which calls `report_init_message()` and emits a new `Grbl ...` startup banner. DDGo accepts at most one reset-associated standalone `ALARM:3`, only after the current-generation Stop coordinator has begun its own Ctrl-X write and before that operation's qualifying startup banner is processed. The banner closes this one-use allowance immediately; duplicate, late, or unrelated alarms invalidate verification. The alarm is not readiness evidence, and the banner plus a fresh current-generation Idle remain mandatory. DDGo requires a current-generation banner newer than the reset write's baseline, then issues a fresh serialized `?` and requires a still-current `Idle` report newer than that status baseline. Only then does it publish `ProgramStopped` and return readiness to Normal. The same caution applies here as to normal completion: firmware `Idle` is DDGo's available synchronization evidence, not independent proof of exact physical cutter position.

Known Hold/reset write failure, missing or stale banner/status evidence, unexpected Alarm, disconnect, generation replacement, e-stop, or expiration of a bounded stop phase fails closed as `RecoveryRequired`; it never produces a confidently finalized Stop. Other than the strictly reset-associated `ALARM:3` above, both standalone `ALARM:n` feedback and `<Alarm|...>` status reports invalidate an in-progress Stop or reconnect readiness check, and the final Stop transition rechecks that latch atomically so a later Idle cannot erase the alarm. Program failure after controller work may have been submitted establishes the same interlock while preserving the run's original `ProgramError`. The supported recovery path is deliberate disconnect and reconnect. Reconnect must pass the existing banner/startup-quiet/`$$` handshake and then produce a newly requested current-generation `Idle`; merely opening the port cannot clear recovery, and stale events from the interrupted generation cannot contribute. No former run resumes after recovery; a subsequent Run is a new execution with a new `RunID`. Automatic reconnect follows the same verification rule.

For ordinary G-code, normal program sending waits on terminal controller responses before advancing acknowledged progress; `ok` acknowledges acceptance and does not prove motion has completed. Intermediate RX lines are ignored by ordinary program sends instead of being buffered as program output. After the last acknowledgement, the separate final-drain synchronization above determines successful completion.

Program-owned commands whose final, trimmed outgoing text begins with `$` are execution barriers. Before transmitting one, the command runtime must observe a new status report (not a previously cached state) reporting `Idle`. After a successful terminal response it must observe another fresh `Idle` before progress or completion can advance. This applies equally to direct program lines and macro-generated queries such as `$#`; interactive/manual command runtimes are intentionally unchanged. Barrier waits retain program/session and connection-generation ownership and wake on stop, disconnect, cancellation, or alarm, while Hold remains a resumable state.

## Frontend document lifecycle

The toolkit-independent frontend document registry owns open-document identity. It allocates a nonzero `DocumentID` once for each logical document and never reuses it, while `WindowManager` continues to own the native top-level window and its registration with the application's single controller-event dispatcher. File-backed documents are keyed by cleaned absolute paths with existing symbolic links resolved (and case-normalized on Windows), so opening an equivalent path focuses the existing window without rereading or replacing its retained source. Closing removes the registry entry only after the native window close has been accepted and WindowManager has unregistered its view; a stale callback for an already-closed document cannot remove a later reopen because the IDs differ.

Execution state is owned by toolkit-independent frontend **execution sessions**, not native G-code windows. A session retains an immutable parsed program, parse result, exact RunID association, controller-derived presentation, pending Run/Pause/Resume/Stop state, and operation errors. Program-line slices are copied when a session is created and again for every observer snapshot, so no caller or view can mutate retained executable content or another observer's snapshot. Detaching a view never clears the session, its RunID, or terminal presentation. This keeps native Qt callbacks from becoming an independent execution history and permits a later view to recover the retained state. The current standalone G-code document creates one session for its nonzero `DocumentID`. A future package step will use a distinct session identity containing the owning package DocumentID, its ordered job index, and stable step ID, so two steps using the same G-code resource cannot consume each other's state.

The application remains responsible for asynchronous controller calls and routes the single revisioned controller event stream into sessions once. A Start result binds its exact RunID to its originating session. If a controller state arrives before that asynchronous result, it is held only while an eligible admission is pending and replayed after exact association; no package step is guessed from a shared DocumentID. Buffered replay updates only the associated run presentation, never the newer globally accepted machine state used for connection/readiness/control policy. Pause, Resume, and Stop additionally require that the session's own RunID exactly match the active controller RunID; a sibling package step therefore cannot borrow controls merely because it has the same DocumentID. The session manager is also the single source of package-owner Run eligibility: while one step has a pending or admitted-but-unreconciled start, it projects that lock into every sibling session snapshot and notifies their attached views immediately. A successful Start remains admission-pending until a controller state for its exact RunID has been reconciled, preventing a second Run click in the post-admission gap; a rejected admission immediately releases eligible siblings. Stale results and errors cannot update a replacement session or run. Document Run acquires the shared frontend program-start gate synchronously in the button callback, then records an outstanding per-session admission before its controller goroutine starts. A close commitment blocks further Run admission for that document. If close is requested while a previously accepted Run is still resolving, native closure is deferred: a failed admission permits a safe retry of the close, while a successful admission returns to the explicit Stop Program and Close decision for that exact run. A close request for an inactive or terminal document proceeds normally. If the current active controller run has the document's `DocumentID`, the window stays open until the operator chooses **Stop Program and Close** and the controller's safe Stop coordinator successfully finalizes the exact `DocumentID`/`RunID`. Hold/Ctrl-X issuance, `ProgramStopping`, or an unresolved recovery state is not sufficient to close the document. A failed stop leaves the document and main control window available for recovery.

Each read-only standalone document window is one view of its standalone session and retains the existing execution panel. `ProgramComplete` is displayed as **acknowledged commands** and maps the next unacknowledged executable instruction back to its physical source line only while the run is Running or Paused, preserving comments and blank lines. Draining, stopping, stopped, completed, and failed runs retain their acknowledged progress but clear the pending-command marker. `ProgramDraining` explicitly reports that all commands are acknowledged while DDGo awaits its required fresh Idle; it does not claim physical motion is complete. Source highlighting is a non-destructive gutter marker, separate from the Follow Execution scrollbar movement; clearing the next command clears the marker. A delayed successful Run-admission result confirms only its Run ID and cannot erase a newer same-run terminal state or run-scoped error. Run-scoped errors require matching event document/run IDs, so a general controller error is not presented as a document failure.

`.dd` packages are now first-class read-only documents. `DocumentRegistry` uses an explicit G-code/package kind while retaining the same canonical-path identity, non-reused `DocumentID`, focus-existing behavior, native-close validation, and shutdown participation. A package owns one logical document entry; its per-job/per-stable-step G-code windows are supplementary native views keyed by the package-step `ExecutionSessionID`, never extra documents. `WindowManager` retains and unregisters each native auxiliary view, while the package-owned auxiliary-view map prevents duplicate windows, makes stale close callbacks token-safe, and closes all supplementary views only after the package's own native close succeeds. Auxiliary windows provide **Back to Package** focus navigation and retain source/session state when individually closed; they have no execution callbacks or enabled execution controls in DD-B2. The package window presents jobs, ordered steps, text/Markdown as safe plain text, bounded in-memory images, resource references, loader diagnostics, and a noninteractive execution strip. Package-step execution, guided navigation, and workflow metadata behavior remain deferred to DD-B3 and later.

The main window is the application anchor and machine-control surface. It has no program-loading or program-execution commands. Its read-only **Current Execution** (or **Last Execution**) summary derives only from controller state accepted by the revision-aware UI dispatcher and reports the program name, status, and acknowledged-command progress. Document lifecycle callbacks refresh only `Show Document` availability; they do not apply a direct controller snapshot or replace the displayed execution state. `Show Document` stores the displayed exact `DocumentID`/`RunID`, then revalidates that identity against a fresh controller snapshot and the document registry before focusing the existing window. It never opens, reloads, or substitutes a document; closure or reopening of the same path makes the old identity unavailable. Document windows retain all program Run/Pause/Resume/Stop controls and their own history. Controller legacy `LoadProgramFile`/`StartProgram` APIs and zero-DocumentID execution remain compatible for tests, tooling, and shutdown, but have no frontend Load/Run workflow.

DDGo also has a toolkit-independent, read-only `.dd` package loader under `internal/ddpackage`. It snapshots and validates archive resources and structured guided-job metadata without creating a document window, controller request, or machine action. Package format, limits, submanifest behavior, and the proposed future document-integration boundary are documented in [dd-package-format.md](dd-package-format.md).

A toolkit-independent shutdown coordinator owns one attempt at a time: application confirmation, optional exact-run Stop confirmation, verified Stop completion, document closure, and finally one committed native main-window close. The shared frontend program-start admission gate registers document Run requests synchronously in the UI callback before their controller goroutine starts. Shutdown freezes that gate, waits asynchronously for all already-admitted starts to return from controller admission, then chooses any required Stop target from a fresh controller snapshot. This does not replace controller admission or mean a successful start has physically completed; it merely prevents a queued frontend start from being invisible to shutdown. Cancelling shutdown reopens the gate, while final native close keeps it permanently closed. The coordinator authorizes native close for exactly one selected document at a time, bound to that attempt; accepted or rejected closure retires the authorization. The UI rechecks that execution is inactive and readiness is normal before accepting that native close. A replacement run, or an external Stop outcome that can no longer be attributed to the original run, cancels the attempt instead of allowing new execution to inherit old close authority. If an independently initiated document Stop finishes during shutdown, its verified result transfers only native-close ownership to shutdown; it does not issue a second Stop or borrow close authorization. A rejected native close clears its pending-close bookkeeping so the document remains usable. Cancelling either confirmation clears that attempt before any document is destroyed; a failed Stop also abandons automatic shutdown and leaves the machine-control interface and affected documents available for recovery. If a Stop has already been accepted, cancelling the UI shutdown does not cancel the physical Stop, but its late result cannot close the application because it carries the old shutdown-attempt ID. Native document close callbacks only update coordinator state; the UI timer performs later close work, avoiding recursive main-window destruction from inside document deletion. Immediately before the final `WA_DeleteOnClose` operation, the coordinator commits an exact-once close flag; later callbacks and results are harmless no-ops. DDGo does not exit while `MachineReadiness` is restricted; recovery must remain available. The Qt6 3D toolpath view remains future work.

## Response collection

DDGo has query-scoped response collection for macro/runtime queries owned by a response session. Program runs own a program execution session, and an interactive macro owns one short-lived interactive command session:

- At most one response owner may exist. Its four states are program, interactive macro, manual line, and none. Program start is rejected while an interactive macro or manual line is active, and interactive macros/manual controls are rejected while a program is active. Every owner and program run records the physical connection generation on which it was admitted, so a terminal response from another generation cannot satisfy or release it.
- Three identities have deliberately separate roles: a Connect-attempt ID identifies one `Controller.Connect` invocation, a connection generation identifies one physical transport connection, and response-owner identity identifies the command session entitled to terminal responses. Every successful physical `Open` allocates a new non-zero, monotonically increasing generation and returns it directly to `Connect`; connection-derived connected, disconnected, RX, TX, and error events are tagged at their source. Serial read loops retain their starting generation rather than consulting mutable active state.
- Connection establishment is an explicit controller admission transition reserved before the potentially blocking transport open. Each `Connect` owns a monotonically allocated attempt identity and a private bounded transport-event queue through initialization, commit, or failure. Events may arrive before `Open` returns; after the candidate generation is known, only its startup banner, settling output, transport failures, and `$$` response can affect validation. Disconnect generations observed before `Open` returns remain correlated with the generation returned by that exact open. Cleanup remains identity-checked, preventing a pre-commit disconnect from being overwritten by connected state or confused with a stale prior attempt.
- The controller accepts RX, TX, errors, and established disconnects only from its committed non-zero connection generation. Thus complete queued RX, disconnect, and error events left by an old physical connection are ignored after reconnect: they cannot alter status, enter normal console traffic, satisfy query/probe collection, advance or fail a program, or mutate lifecycle state. Explicit-close disconnect suppression records the exact generation and can suppress only that generation's event.
- Realtime/control writes use a short-lived, mutex-protected reservation spanning the entire transport write. Connect rejects an active reservation, disconnect first reserves its transition and then waits without holding the mutex for an already-admitted write, and no new response owner can start until the reservation ends. Status, Hold, Resume, Jog Cancel, raw-console/status polling `?`, and Soft Reset use this serialization; polling stops and joins before disconnect closes the transport.
- Manual command-prompt submissions and manual transport actions that could produce controller responses are rejected while an interactive macro owns responses. Automatic status polling remains allowed because it uses suppressed requests and status parsing that cannot complete an application command.
- Explicit and unexpected disconnects synchronously terminate an active interactive macro session with the transport-disconnected sentinel, clear ownership, and wake response waiters without failing an idle loaded program or clearing variables/contour points.
- Soft Reset is a realtime command and does not expect a terminal `ok`, but unlike ordinary realtime controls it invalidates outstanding controller command state. Atomically under the controller mutex, it reserves realtime I/O and then cancels an interactive-macro or manual-line response owner; Ctrl-X is written before the reservation is released, so a replacement owner cannot start in between. An interrupted interactive command wakes with `ErrControllerReset`, including when the reset write itself fails. Generic Soft Reset is rejected while a program is actively executing and while a Stop coordinator is active: that coordinator is the sole authority for its Hold/reset/banner/Idle sequence. A manual reset remains available as a recovery action when no Stop coordinator owns the reset, but a successful Ctrl-X write alone never clears `RecoveryRequired`.
- Machine-wide Resume (`~`) is never a substitute for program Resume. The controller rejects it while a program owns execution, a Stop is active, readiness is restricted, or e-stop admission forbids it. Program Resume is separately run- and generation-aware at the realtime-write reservation, so a delayed request cannot resume a stopped or replacement run.
- Normal program execution does not buffer every RX line.
- When a macro/runtime query is active, the active run temporarily installs a query response channel.
- All RX lines delivered to the active run are also delivered to that query channel until the query completes.
- Query collection returns intermediate lines when the controller eventually responds with `ok`.
- Query collection fails when the controller responds with `error` or `alarm`.
- Only one query collector can be active for a run at a time.
- WCS offset reads use this path by sending `$#` and parsing the collected offset responses.

## Macro framework

The `internal/macro` package provides the application-level macro interception framework plus the current default batch of built-in command handlers. The default controller installs `macro.NewDefaultEngine()`, so registered built-ins are intercepted during both normal program execution and interactive command-prompt submission instead of being sent raw to firmware.

Implemented framework pieces include:

- `macro.Invocation`, which carries the source `gcode.Line`, leading M-code number, `RawArgs`, and `CleanArgs`.
- Raw vs clean argument handling so handlers can choose between original line content and comment-stripped sanitized content.
- `macro.Registry` for registering handlers by leading M-code number.
- `macro.Engine` for parsing a program line and dispatching to a registered handler.
- `macro.Handler` and `macro.HandlerFunc`.
- Typed nil `HandlerFunc` protection.
- `macro.Error`, which wraps handler errors with source line and code context.
- `macro.Runtime`, the controller-facing capability interface exposed to handlers.
- Default handlers for exactly M100, M101, M102, M106, M107, M108, M109, M111, and M112. M103-M105 are intentionally undefined, and M110 is unsupported legacy functionality. Command syntax details live in `docs/macros.md`.

Empty registries and custom macro engines remain available for tests and specialized flows through `SetMacroEngine`.

Current macro behavior includes probe runtime support, M109 contour point collection, and M111/M112 contour lifecycle control. M110 is rejected as unsupported legacy functionality before it can reach the controller from either source. M103-M105 remain intentionally undefined and follow the same pass-through policy as other unregistered commands.

Currently deferred macro behavior:

- Contour surface fitting is not an active project requirement unless separately reintroduced later.
- Contour motion rewriting / Z compensation is not an active project requirement unless separately reintroduced later.

## Contour state

`macro.ContourState` stores contour points and an enabled/disabled lifecycle flag. It rejects duplicate X/Y points. Clearing contour state removes all collected points and disables contour mode.

Program start disables contour mode without clearing collected points. Program failure also disables contour mode without clearing points. Actual contour surface fitting, motion rewriting, and Z compensation are not part of the active project requirements.

## Mock controller

`cmd/mockgrbl` and `internal/mockgrbl` provide a GrblDD-style mock controller for Linux PTY-based integration tests. The mock is intentionally scoped to DDGo development needs: command acceptance, status reports, motion-state simulation, selected `$` queries, probe/WCS helpers, reset/hard-limit behavior, and transport-loss test hooks. Usage details live in [`docs/mockgrbl.md`](mockgrbl.md).
